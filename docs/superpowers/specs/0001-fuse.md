# Spec: Fuse — Multi-Model Agent Harness

## Context

The existing stack has three strong, independent pieces that do not yet speak a common language:

1. **codeindex** — Go-based code navigation engine (blast-radius, call graphs, symbol lookup) with a Claude Code plugin, but not available to any other model
2. **LiteLLM gateway** (`:4000`) — 11 models unified under an OpenAI-compatible API: local Ollama (`local/*`) and OpenRouter cloud (`cloud/*`) models, plus `claude/*` via Anthropic; all confirmed tool-capable
3. **Claude Code** — production-grade agent harness, but Claude-only; other models get a minimal Python script (`model-council.py`) with no parity

The gap: DeepSeek, Qwen, Kimi, GLM, and local models all support function-calling through the gateway, but they run without code navigation, without the skill system, without hooks, and without proper session management. Claude gets a first-class harness; every other model gets a prototype.

Fuse closes that gap. Claude is one model in the ecosystem — a spoke in the wheel — not the designated orchestrator.

## Goals

1. **Model-agnostic runtime** — any configured model can be the primary agent; the harness is not coupled to Claude or any single provider
2. **Code navigation for all** — codeindex tools (`impact`, `callers`, `callees`, `search`) available in the tool registry for every model, same token savings as the Claude Code plugin
3. **Skill compatibility** — SKILL.md files from `~/.claude/skills/`, `~/.grok/skills/`, and `~/.fuse/skills/` all work; skills written for Claude Code run here without modification
4. **Gateway-native** — the LiteLLM gateway is the sole model transport; no per-model adapter code, no duplicate API key handling
5. **Claude as peer** — `claude/sonnet` (and other Claude models) are entries in the model registry like any other; they route through the gateway

## Non-goals (v1)

- A web UI or REST server (CLI only)
- Model fine-tuning or weight management
- Building a new plugin marketplace (use `~/.fuse/skills/` for now)
- Replacing Claude Code for users who prefer it (they coexist)
- Real-time streaming output to a programmatic caller (TTY focus first)

## Architecture

### Binary: `fuse`

Single Go binary. Installed to `/usr/local/bin/fuse`. Statically linked except CGO dependencies (codeindex uses tree-sitter + SQLite via CGO — same requirements as `codeindex` itself).

```
fuse [--model <name>] [--skill <name>] [--session <id>] "<task>"
fuse shell                   # interactive REPL
fuse models                  # list configured models
fuse skills                  # list discovered skills
fuse session list            # list saved sessions
fuse session resume <id>     # resume a session
```

## Core agent loop

```go
// internal/agent/loop.go
func (a *Agent) Run(ctx context.Context, task string) error {
    messages := []Message{{Role: "user", Content: task}}

    for turn := 0; turn < a.config.MaxTurns; turn++ {
        a.hooks.Fire(PreTurn, HookCtx{Turn: turn, Messages: messages})

        resp, err := a.model.Complete(ctx, CompletionReq{
            Messages:   messages,
            Tools:      a.tools.Schemas(),
            MaxTokens:  a.config.MaxTokens,
        })
        if err != nil {
            return err
        }

        a.tui.RenderAssistant(resp.Content)
        messages = append(messages, resp.AsMessage())

        if len(resp.ToolCalls) == 0 {
            a.hooks.Fire(Stop, HookCtx{Final: resp.Content})
            return nil
        }

        for _, call := range resp.ToolCalls {
            a.hooks.Fire(PreToolUse, HookCtx{Tool: call})
            result := a.tools.Execute(ctx, call)
            a.hooks.Fire(PostToolUse, HookCtx{Tool: call, Result: result})
            a.tui.RenderToolResult(call, result)
            messages = append(messages, toolResultMessage(call.ID, result))
        }
    }

    return ErrMaxTurnsReached
}
```

Key properties:
- **Stateless turns** — the loop is pure function over messages; resuming a session is appending to the messages slice
- **Context cancellation** — every tool execution respects `ctx`; long-running bash commands can be interrupted
- **Loop detection** — identical consecutive tool-call fingerprints abort after 3 repeats (proven necessary from model-council.py experience with thinking models)

## Tool registry

Tools are registered with their JSON Schema, executed by name. Every model sees the same tool set.

| Tool | Inspired by | Description |
|---|---|---|
| `bash` | Claude Code, Grok Build | Shell execution; timeout; working directory |
| `read_file` | Claude Code, Grok Build | Read file content with optional line range |
| `write_file` | Claude Code | Create/overwrite a file |
| `edit_file` | Claude Code | Surgical edit: old_string → new_string with uniqueness check |
| `web_search` | Claude Code | Tavily search API; respects `TAVILY_API_KEY` |
| `codeindex_impact` | codeindex plugin | Callers + callees for a symbol; blast-radius pre-edit |
| `codeindex_callers` | codeindex plugin | Direct callers of a symbol |
| `codeindex_search` | codeindex plugin | Semantic/lexical symbol search |
| `list_directory` | Claude Code | Directory listing with optional glob |
| `spawn_subagent` | Grok Build | Spawn a child agent; returns when done or hits max turns |

### `codeindex` integration

The harness calls the `codeindex` binary (must be on PATH or `CODEINDEX_BIN`). Same requirement as the Claude Code plugin. The integration wraps the same three operations (`impact`, `callers`, `search`) with identical output format — so skills and hooks written for the Claude Code codeindex plugin work unmodified in the harness.

The post-edit hook from the codeindex plugin is also ported: after any `edit_file` or `write_file` call that touches a known symbol, inject a ≤150-token blast-radius note (same as the Claude Code plugin, measured to increase branch-out rate by 62%).

### `spawn_subagent`

```go
type SubagentReq struct {
    Model          string   // e.g. "local/qwen3-coder:30b"; defaults to config.subagent_default
    Task           string
    CapabilityMode string   // "read-only" | "read-write" | "execute" | "all"
    Worktree       bool     // isolate in a fresh git worktree
    Tools          []string // override: empty = inherit parent tool set
}
```

This is what makes multi-model composition possible. Example: a DeepSeek primary agent spawns a `local/qwen3-coder:30b` subagent for a specific refactor, then a `cloud/kimi-k3` subagent for a research step.

## Skills system

Skill discovery scans three paths in order:
1. `~/.fuse/skills/`
2. `~/.claude/skills/` (Claude Code compatibility)
3. `~/.grok/skills/` (Grok Build compatibility)

Each directory entry that contains a `SKILL.md` is a skill. SKILL.md frontmatter:
```yaml
---
name: codeindex:impact
description: Blast-radius navigation for a symbol
triggers:
  - when: "editing a function or type"
    auto_invoke: true
slash_command: /codeindex:impact
---
```

Skills are injected into the agent's system context (for auto-invoke) or triggered by slash command in the shell. Same mechanism as Claude Code and Grok Build — skills written for either work here.

**Built-in skills (shipped with the harness):**

| Skill | Slash command | Description |
|---|---|---|
| `multi-model:route` | `/route` | Analyze a task and recommend which model to use |
| `multi-model:compare` | `/compare` | Run the same task on two models; diff the results |
| `docket:status` | `/docket` | Show the current project's docket board |
| `docket:new` | `/docket:new` | Start a new docket change from within a harness session |
| `codeindex:impact` | `/impact` | Blast-radius for a symbol (proxied from codeindex plugin) |
| `codeindex:explore` | `/explore` | Feature exploration: semantic search → impact |
| `session:summary` | `/summary` | Summarize current session for handoff |

## Hooks

Hook schema is compatible with Claude Code's `hooks.json` format. Hooks live in `~/.fuse/hooks.json` or per-skill `hooks.json` files. Events:

| Event | Timing | Blocking |
|---|---|---|
| `PreToolUse` | Before any tool executes | Yes (can reject/modify) |
| `PostToolUse` | After tool returns | No |
| `Stop` | When agent finishes | No |
| `SessionStart` | On session open | No |
| `SubagentStop` | When a subagent finishes | No |
| `UserPromptSubmit` | Before sending user message to model | Yes (can inject context) |

The codeindex plugin's `UserPromptSubmit` hook (the 155-token availability note) and post-edit hook work unmodified through this system.

## Key design decisions

**Go over TypeScript/Python:** codeindex is Go with a Go SDK; native library integration avoids subprocess overhead for every code navigation call. Go's single-binary distribution means `go build -o /usr/local/bin/fuse ./cmd/fuse` is the entire install. CGO is already required by codeindex anyway.

**Gateway-only model access:** All models route through the LiteLLM gateway. This means the harness has zero model-specific adapter code. Adding a new model is one line in `~/.fuse/config.yml`. The gateway handles retry, logging, cost tracking, and OpenAI-compat normalization.

**No Claude orchestrator:** Routing decisions are made by explicit flag, rule-based auto-routing, or a lightweight built-in skill (`/route`). Claude does not have a privileged position. Any model can invoke any tool. Any model can spawn subagents. This is the architectural difference from model-council.py.

**SKILL.md compatibility as a first-class goal:** The skill file format must be byte-compatible with Claude Code's format. This way, any skill developed for Claude Code works in the harness, and any skill developed for the harness works in Claude Code. The harness grows the shared skill ecosystem rather than forking it.

## UX & TUI

The harness is designed around a single primary experience: `fuse shell`, a chat-first REPL you stay inside the way you'd stay in Claude Code. Everything in this section describes that experience. The one-shot `fuse "<task>"` invocation (see Architecture) reuses the same rendering primitives but without the two-pane layout, sidebar, or mouse interaction — it streams a single agent run to the TTY and exits.

The TUI is built on **bubbletea** (Charm ecosystem), with **lipgloss** for styling and **bubbles** for reusable components (viewport, textinput). This replaces the minimal `internal/tui/renderer.go` sketched in the Architecture section with a full bubbletea model; `renderer.go` and `spinner.go` become the render helpers that bubbletea's `View()` composes.

### Interaction model: chat-first REPL

`fuse shell` is the primary entry point. The session is a running conversation: context accumulates across turns, and each user prompt is appended to the same message history the agent loop operates on (see Core agent loop). There is no per-turn reset — the loop's stateless-turn property means the REPL is simply a long-lived message slice that the human extends between agent runs.

The human types a prompt, the active model runs an agent loop (thinking, tool calls, results, prose), and control returns to the input bar. Slash commands (`/model`, `/spawn`, `/verbose`, and the built-in skill commands from the Skills section) are interpreted by the REPL before the message reaches the model; everything else is a prompt.

**Session pane (left).** A scrollable transcript of the conversation: user prompts, model response blocks (each opened by a model header, see below), tool-call lines, and subagent blocks. This is the region that grows during a run and the one the mouse wheel scrolls. New output auto-scrolls to the bottom unless the human has scrolled up, in which case position is held (standard chat behavior).

**Sidebar (right).** Three stacked sections — *artifacts*, *change metadata*, *models* — each described below. The sidebar is ambient context, not conversation: it reflects the current state of the session, the docket change, and the model roster, and every row in it that maps to an action is clickable.

**Input bar (bottom).** Full width. Renders the prompt `[model-name] >` in the active model's color (see Visual identity) followed by the text cursor. Accepts multi-line input; submit on Enter, newline on Shift+Enter.

The chat/sidebar split has a default ratio (chat wider than sidebar) that the human can drag to change. If the terminal is too narrow to render both panes legibly, the sidebar collapses and its content becomes reachable through slash commands (`/artifacts`, `/change`, `/models`); the exact minimum-width threshold is an implementation detail.

### Model switching

Three modes, all operating on the same accumulating conversation.

| Mode | Trigger | Effect |
|---|---|---|
| Launch-time | `fuse shell --model deepseek-flash` | Sets the primary model for the session before the first prompt |
| Mid-session swap | `/model kimi` | Hands the full conversation history to the named model; it continues from where the last model left off |
| Subagent spawn | `/spawn qwen-coder "refactor internal/agent/loop.go"` | Fires a child agent on a scoped task; result returns to artifacts; the primary session and its model are untouched |

**Launch-time** resolves `--model` against the model registry (Model registry section) and, absent the flag, falls back to `models.default` from config.

**Mid-session `/model`** is a hand-off, not a reset: the new model receives the existing message history and any loaded system context (including a docket change spec, if one was loaded — see Docket session start). The moment the swap takes effect, the input-bar prompt color and all subsequent response headers change to the new model's identity, so the human never has to guess who is answering. Prior turns in the transcript keep the header color of whichever model produced them.

**`/spawn`** is the shell surface over `spawn_subagent` (Tool registry). It does not change the primary model; it launches a scoped child, renders its progress inline (see Subagent inline progress), and deposits its result in the artifacts panel. The primary session continues to accept prompts — the spawn is asynchronous from the human's point of view, and its inline block updates in place as the child runs.

### Visual identity system

Every model has a stable color. The color is the primary signal for "who is acting," and it appears in three places: the input-bar prompt, the response header that opens each model turn, and the active-model bullet in the models roster.

**Prompt.** The input bar renders `[model-name] >` in the active model's color.

**Response header.** Each model response opens with an inline rule carrying the model name:

```
── deepseek-flash ──────────────
```

rendered in the model's color. The header delimits turns visually and makes a mid-session `/model` swap unmistakable in the transcript.

**Color assignment.** Colors follow the model, not the provider slot, so switching models changes both the prompt and every subsequent header. A default palette assigns:

| Model / family | Color |
|---|---|
| DeepSeek (flash, pro) | blue |
| Kimi | purple |
| Claude | orange |
| Local models (Ollama: qwen-coder, qwen-local, llama, gemma, mistral-nemo, codellama) | green |
| GLM, Qwen cloud, other cloud | assigned from a remaining-color pool, stable per model |

Assignments are deterministic per model name so a given model always looks the same across sessions. The palette is overridable in config (an optional `ui.colors` map, model-name → lipgloss color); the defaults above ship built-in. Colors are chosen to remain distinguishable on both dark and light terminals; on terminals without color support the headers still render (name + rule) so identity survives degradation.

### Tool call display

Tool activity is rendered as visually distinct lines, set apart from model prose so the human can scan "what the agent *did*" separately from "what the agent *said*."

- **Call start:** `→ tool_name(args preview)` — the arrow, tool name, and a truncated preview of the salient argument (e.g. the target path for `write_file`, the command for `bash`).
- **Result:** `← result preview` — a truncated summary (e.g. `created · 87 lines`, `3 hunks`, exit code).

Both lines are truncated by default to keep the transcript scannable. Full output is available two ways:

- `/verbose` toggles verbose mode for the rest of the session (subsequent tool blocks render full args and full output).
- `--verbose` at launch (`fuse shell --verbose`) starts in verbose mode.

Tool blocks use a distinct lipgloss style (dimmed / bracketed relative to prose) so that even in verbose mode they read as machine activity rather than model narration.

### Sidebar sections

Three stacked sections, top to bottom: **artifacts**, **change metadata**, **models**. Each is populated at session start where applicable and updated live as the session proceeds. Interactive rows respond to click and carry a hover state (lipgloss styling on mouse-over).

#### Artifacts

Every file created or significantly modified during the session, plus results returned by subagents. The list grows as the session produces output — each successful `write_file`, `edit_file`, and subagent result adds (or refreshes) an entry.

Entries are file paths rendered as clickable links (marked `↗`). Clicking a file opens it in `$EDITOR`; where opening in an editor is not possible (no `$EDITOR`, or a headless environment), the click copies the absolute path to the clipboard as a fallback. Files are grouped by directory for legibility when the list is long.

#### Change metadata

The active docket change, detected at session start by mapping the current git branch to a `feat/<slug>` change in `.docket/docs/changes/active/` (per docket's branch model). When a match is found, this section shows:

| Row | Source | Click action |
|---|---|---|
| Status badge | `status:` frontmatter in the change file | — |
| Branch name | current branch → mapped change | `git checkout <branch>` |
| Worktree path | docket worktree convention for the change | open in Finder / shell |
| PR number + status | `gh pr list` query at session start (draft / review requested / approved / merged) | open the PR's GitHub URL in the browser |
| Open question count | count of unresolved items under `## Open questions` in the change file | — |

All rows are populated once at session start from the change file plus a single `gh pr list` query. The section does not poll; it reflects the state as of session open.

When the current branch maps to no active docket change, this section renders a single muted line (`no active change`) rather than an empty box.

#### Models

The full configured model roster (from the Model registry). Each entry is a model name preceded by a status bullet:

- `●` — the active primary model
- `○` — an idle configured model

Recently-used models show their last-used turn number (`○ kimi (turn 4)`). Clicking a model name runs `/model <name>` — the roster is a click-to-switch control. The active bullet moves and its color updates the instant a swap takes effect, in lockstep with the prompt and header color change.

### Docket session start

When `fuse shell` opens inside a docket project and the current branch maps to an in-progress change, the shell shows a session banner and loads the change's spec into the model's system context automatically:

```
  Fuse  deepseek-flash
  ──────────────────────────────────────────
  📋 Change 0001 — Fuse Multi-Model Agent Harness
     in-progress  ·  feat/fuse-agent-loop  ·  4 open questions
  ──────────────────────────────────────────
  Session context loaded. What are we building?

[deepseek-flash] >
```

The banner names the harness, the active model, and a one-line summary of the detected change (id, title, status, branch, open-question count). The change's linked spec is read and injected into the primary model's system context at startup — no manual copy-paste. On a mid-session `/model` swap, the loaded change context travels with the conversation to the new model.

When the shell opens outside a docket project, or on a branch with no active change, the banner degrades to a plain header (`Fuse  <model>`) with no change line, and no spec is injected. The shell is fully usable without docket; docket simply enriches it.

### Subagent inline progress

`/spawn <model> "<task>"` renders a collapsible progress block inline in the session pane while the child agent runs:

```
  ▸ subagent: qwen-coder — "refactor internal/agent/loop.go"
    → read_file(internal/agent/loop.go)
    → edit_file(internal/agent/loop.go) · 3 hunks
    ← done · added to artifacts
```

The block's header names the subagent model and its scoped task. Tool-call lines stream into the block as the child works. On completion the block collapses to its one-line header; clicking the header re-expands it to review what the child did. The subagent's result is added to the artifacts panel. The primary session remains interactive throughout.

| Drag the pane divider | Resize the chat/sidebar split; the new ratio holds for the session |
| Mouse wheel over the session pane | Scroll the transcript |
| Click a file in artifacts | Open in `$EDITOR` (fallback: copy path to clipboard) |
| Click a branch row (change metadata) | `git checkout <branch>` |
| Click a worktree row | Open the worktree in Finder / shell |
| Click a PR row | Open the PR's GitHub URL in the browser |
| Click a model name (roster) | Run `/model <name>` |
| Click a collapsed subagent block | Re-expand it |
| Hover any interactive element | Hover state (lipgloss styling) |

Every mouse action has a keyboard-reachable equivalent (slash commands, scroll keys, tab/focus navigation). Terminals or multiplexers that don't forward mouse events lose no capability.

### Auto-detection (zero-config start)

`fuse shell` launches with no config file required. On startup it reads `LLM_GATEWAY_URL` and `LLM_GATEWAY_KEY` from the environment and connects to the gateway directly. With no `~/.fuse/config.yml` present, the shell falls back to the built-in default model registry and a built-in default model.

`~/.fuse/config.yml` is an **optional override**: it exists to customize model aliases, change the default model, remap the color palette (`ui.colors`), add custom skill paths, or configure subagent defaults. Its absence never blocks launch.

### Assumptions

1. **bubbletea is the confirmed TUI framework.** The two-pane layout, mouse events, drag-to-resize, and collapsible blocks all assume bubbletea + lipgloss + bubbles are acceptable dependencies. CGO constraints (already present via codeindex) don't conflict with them.

2. **Docket project structure is stable.** Change files live under `.docket/docs/changes/active/`, carry `status:` frontmatter and `## Open questions`, link to their spec, and map to `feat/<slug>` branches. Change detection reads these directly.

3. **`gh` CLI is available and authenticated** for PR metadata. If absent or unauthenticated, the PR row degrades to a muted "unavailable" state; the rest of the sidebar is unaffected.

4. **Clickable links resolve via `$EDITOR` / OS handlers, with clipboard fallback.** Opening files, worktrees, and PR URLs assumes `$EDITOR`, `open`/`xdg-open`, and clipboard access are available. Missing handlers fall back to clipboard copy.

5. **Model colors are deterministic per model name.** The default palette is a starting point; exact lipgloss color values are an implementation detail, provided assignment stays stable per model and degrades on no-color terminals.

6. **Spec injection at session start is a system-context load, not summarization.** The spec is injected verbatim; size/truncation is delegated to `internal/session/compress.go`.

7. **Sidebar reflects session-open state plus live session output.** Artifacts and the models roster update live; change metadata is a snapshot from session start. Live PR/change refresh and the end-of-session flow are out of scope and deferred.

8. **Narrow-terminal degradation collapses the sidebar.** Below a minimum legible width the sidebar hides; `/artifacts`, `/change`, `/models` surface the same content in the session pane. The exact threshold is an implementation detail.
