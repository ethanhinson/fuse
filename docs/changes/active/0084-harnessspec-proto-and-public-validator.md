## Why

A fuse harness (models, skills, MCP servers, permissions, agents, workflows, throughput, context management, caps) is defined today only by internal/config's YAML loader. Any client of the runtime other than the local CLI - the Go SDK, the TS SDK, a remote caller of the networked binding - has no portable, versioned, IDL-defined way to build, serialize, or validate a harness. The config also mixes the client-settable harness surface with operator-only trusted settings (loop_server auth and issuers, tool_identity signing keys, observability, sandbox substrate, host paths) that ADR-0006 keeps out of reach of lower-trust sources. A protobuf HarnessSpec that covers only the client-settable surface encodes that trust boundary in the type: a spec cannot even express an operator-only setting. Because the validator must be importable from outside the fuse Go module, it and its generated stubs must live at public import paths, not under internal/.

## What changes

- New protobuf package fuse.harness.v1 (proto/fuse/harness/v1) next to fuse.loop.v1, generated by the existing buf setup into committed Go and TS stubs: HarnessSpec over the client-settable config surface, field options carrying UI-hint metadata for clients that render a spec as a form (label, help, widget kind, secret_ref marker, tighten_only marker, enum display names), protovalidate per-field shape rules shared by Go and TS, and a HarnessService.ValidateHarness RPC definition (not mounted on any binding).
- Public Go packages: generated stubs at github.com/ethanhinson/fuse/harness/v1 and a validator library at github.com/ethanhinson/fuse/harness exposing Validate(spec) -> []Violation{FieldPath, Message, RuleID}, combining protovalidate rules with the existing internal/config semantic rules (reused, not duplicated) and field paths a form can place errors against.
- Internal Go mapping between config.Config and HarnessSpec in both directions with round-trip tests; internal/config stays the authority for merge semantics and validation, refactored only to expose its existing rules as structured, path-carrying problems. YAML loader behavior is unchanged.
- TS: generated harness types exported from the @fuse/sdk package.
- ADR recording the decision.

## Out of scope

- Runtime consumption of a HarnessSpec (StartLoop taking a spec or spec revision, revision storage, skill-ref resolution) - a later change.
- Mounting HarnessService on loop-serve-net or any binding.
- Any change to the YAML loader, .fuse.local.yml trust rules, or CLI behavior.
- Secret storage or resolution backends (the spec carries secret_ref names only).
